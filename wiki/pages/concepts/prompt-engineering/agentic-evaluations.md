## การประเมินผลเอเจนต์ (Agentic Evaluations)

การทำ Evaluation สำหรับเอเจนต์นั้นทำยากกว่าโมเดลทั่วไป เพราะเอเจนต์มีพฤติกรรมที่ไม่ตายตัว (non-deterministic behavior) ในสภาพแวดล้อมที่เปลี่ยนแปลง คำแนะนำคือ **ให้เริ่มจากชุดทดสอบขนาดเล็กๆ ก่อน (Small Eval)** ไม่จำเป็นต้องทำระบบ Automation ขนาดใหญ่ตั้งแต่แรก

### รูปแบบการตั้ง Eval สำหรับเอเจนต์ (Evaluation Methods)

#### 1. LLM as a Judge (ใช้ AI ตรวจสอบโดยมีเกณฑ์ล่วงหน้า)

เนื่องจากผลลัพธ์ของเอเจนต์มักเป็นข้อความขนาดยาวที่มีรูปแบบไม่ตายตัว การใช้สคริปต์ตรวจความถูกต้องแบบ String Matching ปกติจะพังได้ง่าย จึงใช้โมเดลระดับท็อปอีกตัวมาเป็นกรรมการตรวจแทน

- **ตัวอย่างพรอมต์ของกรรมการ (Judge Prompt):**
```markdown
คุณมีหน้าที่ตรวจรายงานของเอเจนต์วิเคราะห์รถยนต์ จงให้คะแนน Pass หรือ Fail ตามเกณฑ์ต่อไปนี้: 
1. รายงานต้องมีการประเมินปริมาณความจุของรถ Rivian R1S 
2. ตัวเลขการคำนวณจำนวนกล้วยที่ใส่ได้ ต้องอยู่ระหว่าง 10,000 ถึง 50,000 ผลเท่านั้น (หากต่ำกว่าหรือสูงกว่านี้ให้ Fail) 
3. มีการระบุแหล่งอ้างอิงที่น่าเชื่อถืออย่างน้อย 2 แหล่ง
```

#### 2. Tool Use Accuracy (ตรวจสอบพฤติกรรมการเรียกใช้เครื่องมือ)

เขียนโปรแกรมเช็คจากประวัติการทำงาน (Execution Logs) โดยตรง เพื่อควบคุมพฤติกรรมเอเจนต์

- **ตัวอย่างเกณฑ์:** หากผู้ใช้สั่งให้ *"จองตั๋วเครื่องบินข้ามประเทศ"* -> สคริปต์หลังบ้านต้องตรวจเจอการเรียกใช้ฟังก์ชัน `search_flights` อย่างน้อย 1 ครั้ง และต้องไม่มีการเรียกใช้ฟังก์ชัน `confirm_payment` จนกว่าจะได้รับข้อมูลไฟลท์บินเรียบร้อยแล้ว

#### 3. State-based Evaluation (การตรวจสอบสถานะสุดท้ายของระบบ)

วิธีที่แม่นยำที่สุดสำหรับงานวิศวกรรมซอฟต์แวร์ คือการไม่สนใจสิ่งที่เอเจนต์อธิบายระหว่างทาง แต่ตรวจสอบ **"ผลลัพธ์สุดท้ายในโลกความเป็นจริง (Final State Change)"** เช่น ในโปรเจกต์โอเพนซอร์สอย่าง Swe-bench

- **ตัวอย่างสถานการณ์:** สั่งเอเจนต์ลูกค้าสัมพันธ์ว่า *"ลูกค้าต้องการเปลี่ยนวันเดินทางในตั๋วจากวันที่ 25 เป็นวันที่ 28"*
- **วิธีตรวจ Eval:** หลังเอเจนต์รันจบกระบวนการ ให้เขียนโค้ด Python เข้าไป Query ในฐานข้อมูล SQL จริงๆ เพื่อดูว่าค่าในคอลัมน์ `departure_date` ของลูกค้ารายนั้นเปลี่ยนเป็น `2026-05-28` แล้วจริงหรือไม่ ถ้าฐานข้อมูลเปลี่ยน = ผ่าน (Pass)
```
